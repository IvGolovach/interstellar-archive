# Artifact Policy

This repository mixes authored research material with deterministic generated baselines.
That is acceptable only if the boundary stays explicit.

## 1. Source of Truth Categories

### Authored source

These files are written and reviewed directly:

- `README.md`, root policy docs, and `engineering/`
- `mission/`, `parameters/`, `evidence/`, `models/`, `sim/`, `scripts/`, `tests/`
- `web/src/` and supporting web build configuration

### Ephemeral generated outputs

These files are runtime outputs and are not repository truth:

- `ops/reports/`
- `web/dist/`
- `web/node_modules/`
- `.tmp/`
- `__pycache__/`

They may be created during local work or CI, but they are not part of the public repository contract.

## 2. Update Rules

1. Update authored source first.
2. Regenerate tracked baselines only through the canonical scripts in `scripts/`.
3. Run `make check` before proposing tracked generated changes.
4. Treat unexpected artifact drift as a blocking event until explained.
5. Keep canonical `parameter_id` values stable; internal code-literal audit entries must use symbolic ids, not legacy line-based names.
6. Keep parameter visibility in the registry (`visibility`, `public_surfaces`, `audit_scope`), not in ad hoc builder prefix rules.
7. Keep capsule survivability rows generated by `scripts/build_capsule_survivability_artifact.py`; do not hand-edit row probabilities or source-data payloads.
8. Keep capsule risk-budget, mission-feasibility, user-run catalog, mission-probability-coupling, uncertainty-interactions, evidence-upgrade-campaign, optimization-v2, Mission DAG v2 boundary, cost/procurement/architecture feasibility, external-validation review-pack, public-narrative hardening, external-proof-phase, external-reproduction, external-evidence-intake, and roadmap-closure artifacts generated by their builders; do not hand-edit risk rows, feasibility rows, run rows, coupling rows, interaction rows, campaign rows, optimization candidates, module-boundary rows, cost/procurement rows, review cases, proof gates, claim rules, replacement guidance, closure statuses, evidence gaps, record counts, or public claim boundaries.

## 3. Why Tracked Generated Files Exist

Tracked generated baselines are kept when they satisfy at least one of these conditions:

- they are consumed directly by the web UI,
- they consolidate multiple tracked baselines into one stable browser-facing payload,
- they back public badges or release metadata,
- they provide compact baseline evidence that reviewers can diff,
- they encode deterministic contracts that CI must enforce.

If a generated file is only useful as transient debug output, it belongs in `ops/reports/` or CI artifacts, not in the tracked tree.

## 4. Validation Contract

The canonical repository validation entrypoints are:

- `make check`
- `python3 scripts/ci/check_suite.py`

Both flows validate the required file manifest in `docs/required_paths.v1.json` and enforce no-drift checks for the diff-gated tracked generated baselines that are part of the public contract.
