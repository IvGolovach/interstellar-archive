# Architecture

## 1. System boundaries

In scope:
- Deterministic physics/model calculations for documented claims.
- Evidence artifact generation and integrity manifests.
- Governance and reproducibility enforcement.
- Deterministic browser simulation with schema-driven inputs.

Out of scope:
- Real mission operations.
- Real-time telemetry.
- Hardware control or flight software.
- Full-fidelity orbital/thermal/plasma simulation.

## 2. Core components

1. `models/`
- `core_physics.py`: deterministic numerical primitives.
- `claim_calculations.py`: derived claim-level values.
- `evidence_io.py`: registry loading and path access.

2. `sim/`
- `sim/core/*`: internal deterministic engine implementation.
- `sim/public/*`: stable browser-facing simulation boundary that re-exports allowed runtime/types for `web/`.
- `sim/schema/sim_schema.v1.json`: parameter contract.
- `sim/scenarios/*.json`: scenario registry.
- `sim/golden/*`: golden output and checksum.

3. `web/`
- `web/src/app/*`: hash-routed workspace shell and navigation.
- `web/src/pages/*`: lazy route entrypoints for Mission, Parameters, Failure Surface, and Optimization.
- `web/src/ui/*`: presentation and interaction only.
- `web/src/lib/schema_loader.ts`: schema/scenario validation and input assembly through `sim/public`.
- `web/src/lib/parameter_drilldown_loader.ts`: thin reader over the consolidated browser dataset contract.
- `web/scripts/*`: node-side validation/golden/local artifact utilities.

4. `artifacts/`
- tracked deterministic baselines generated by canonical scripts.
- `artifacts/browser_dataset.v1.json`: single browser-facing dataset assembled from tracked generated drilldown, failure-surface, objective, and optimization baselines.
- `artifacts/capsule_survivability_lab.v1.json`: generated capsule target/time/velocity/profile scenario table used by Capsule Lab.
- `artifacts/uncertainty_interactions.v1.json`: generated pairwise uncertainty interaction screen used by the Uncertainty route.
- `artifacts/evidence_upgrade_campaign.v1.json`: generated evidence-review campaign used by the Evidence route; browser detail rows are public-only while internal audit rows remain aggregate counts.
- Browser-facing parameter artifacts intentionally expose registry-visible mission/design/environment parameters only; internal model literals remain in canonical registries as audit-only entries and are excluded from the public workspace surface.
- `artifacts/public/*`: stable import boundary that exposes browser-safe artifact contracts to `web/`.

5. `scripts/`
- `build_evidence_artifacts.py`: artifact build pipeline.
- `build_evidence_status.py`: evidence completeness/trust distribution status artifact.
- `build_browser_dataset_artifact.py`: consolidates tracked browser-facing baselines into a single dataset.
- `build_capsule_survivability_artifact.py`: builds the capsule design and deep-time survivability scenario artifact.
- `run_golden.py`: Python golden run validation.
- `benchmark_compare.py`: baseline comparison.
- `audit_claim_chain.py`: claim-chain consistency audit.
- `mission_baseline_check.py`: thin CLI wrapper over `mission/baseline/*`.
- `ci/evidence_validate.py`: thin strict wrapper over `mission/evidence_validation.py`.

6. `mission/`
- `MISSION_SCHEMA_v1.json`: formal mission contract.
- `BASELINE_SCENARIO_v1.json`: canonical mission baseline input.
- `EVIDENCE_SCHEMA_v1.json`: formal evidence data contract.
- `EVIDENCE_REGISTRY_v1.json`: parameter-to-source/trust bindings.
- `UNCERTAINTY_MODEL_v1.json`: distribution/bounds contract used by evidence validation.
- `baseline/*`: public deterministic mission-baseline library.
- `guards/*`: public realistic/speculative and optimization guard layer.
- `evidence_validation.py`: canonical evidence validator shared by CLI and tests.
- `*_v1.md` documents: mission definitions, uncertainty model, success metric, correction model, and review report.
- `capsule/*`: public capsule material stack, mass closure, and survivability-facing design inputs.
- `survivability/*`: provenance-tagged reduced-order capsule survival engine.

## 4. State transitions

Python evidence:
`IDLE -> GENERATED -> VALIDATED -> BENCHMARKED`

Web simulation:
`IDLE -> PARAMETERIZED -> RUN -> CHECKSUMMED -> VERIFIED`

Failure in any stage transitions to `FAILED` and should block merge via CI.

## 5. Persistence model

Persistent tracked data:
- Source registries (`evidence/`).
- Deterministic model code (`models/`, `sim/`, `artifacts/public/`).
- Stable artifact packs (`artifacts/evidence-pack-v1/*`, `artifacts/browser_dataset.v1.json`, `sim/golden/*`).
- Benchmark definitions (`benchmarks/*`).

Non-persistent local data:
- Operational logs and run outputs in `ops/reports/**` (gitignored).

## 6. External dependencies

Runtime dependencies:
- Python standard library.
- Node.js + npm for web simulation tooling.
- Git executable for commit linkage.

CI dependencies:
- GitHub Actions runners.
- Python 3.11.
- Node.js 20.

## 7. Failure surfaces

1. Registry inconsistency.
2. Numeric drift from deterministic baseline.
3. Artifact integrity break (checksum mismatch).
4. Governance drift (policy-required docs not updated).
5. Scenario/schema contract violations.
6. Golden output drift without intentional schema/model versioning.
7. Silent golden mutation without governance rationale.
8. Mission schema/scenario drift (invalid mode separation, missing uncertainty distributions).

## 8. Core vs UI separation (web sim)

Hard separation contract:
- `sim/core/*` contains simulation logic only and is not imported by `web/` directly.
- `sim/public/*` is the only browser-facing simulation surface.
- `artifacts/public/*` is the only browser-facing artifact surface.
- `web/src/app/*` and `web/src/pages/*` compose screens, but page routes still consume only public sim/artifact boundaries.
- `web/src/ui/*` contains UI rendering only.
- UI calls `runSimulation(input)` and never re-implements formulas.
- UI consumes one consolidated browser dataset instead of stitching multiple raw artifacts at runtime.
- Selected mission-run pages render committed catalog and runtime-generation recipe artifacts only; local review packs under `ops/reports/user-mission-runs/` are generated evidence, not browser truth.
- Mission probability pages render committed coupling rows only; React must not close external target, environment, or recovery factors into a full mission probability.
- Public parameter pages must not mix internal model literals into the browser-facing parameter ontology. The source of truth is parameter registry visibility metadata, with `code_literal.*` retained as a safety guard.
- Parameter form is generated from schema metadata; no per-parameter handcoded UI.

## 9. Invariants and warning surfaces (web sim)

Web sim invariants:
- `runSimulation` must be deterministic for identical input.
- `SimOutput.invariants_passed` must reflect internal checks.
- `SimOutput.golden_checksum` must match committed checksum for `default.v1`.
- `SIM_ENGINE_VERSION` and `schema_version` are explicit model-evolution contracts.

Warning surface:
- Any non-default `non_physical` parameter triggers a prominent warning in UI and output warnings list.

## 10. Model Evolution Protocol

Versioned model evolution is required for any intentional golden change.

Required sequence:
1. Update model/schema logic.
2. Increment `SIM_ENGINE_VERSION` and `schema_version`.
3. Regenerate golden output/checksum and baseline registry.
4. Append rationale to `engineering/CHANGELOG.md` and `engineering/DECISIONS.md`.
5. Pass golden integrity enforcement, drift guard, and negative proof in CI.

## 11. Mission Model Layer

Mission-definition v1 is intentionally independent from `sim/core/*`.

Layer responsibilities:
1. Define horizon-crossing objective with explicit equations and units.
2. Enforce realistic/speculative separation via schema fields (`mission_mode`, `speculative_overrides`, `parameter_tags`).
3. Encode uncertainty as explicit distributions, not single-point placeholders.
4. Compute deterministic baseline outputs for CI and public review.

Contract boundary:
- Mission layer may evolve docs, schema, and validation scripts.
- Public mission APIs live in `mission/baseline/*`, `mission/guards/*`, and `mission/evidence_validation.py`.
- Mission layer must not modify simulation golden integrity unless explicitly versioned under existing policy.

## 12. Realistic vs Speculative Dual-Mode Contract

Mission execution exposes two explicit modes:
1. `realistic`: speculative/non-physical parameters are force-clamped to neutral baselines and cannot affect `core_probability`.
2. `speculative`: speculative parameters are allowed and output is explicitly labeled.

Runtime enforcement:
1. `scripts/mission_baseline_check.py --mode dual` emits split results (`REALISTIC RESULT` and `SPECULATIVE RESULT`) with no merged hidden score.
2. `scripts/ci/parameter_domain_guard.py --strict` validates domain metadata and proves realistic invariance under speculative perturbations.
3. `scripts/optimization_guard.py --strict` blocks optimization plans that tune speculative or trust-`D` parameters.

Output contract additions:
- `mode`
- `speculative_parameters_used`
- `core_probability`
- `trust_weighted_score`

## 13. Optimization Engine Layer (v1)

Purpose:
1. Solve a constrained optimization problem over realistic mission parameters.
2. Produce Pareto frontier and ranked candidates with explicit constraint traces.
3. Preserve deterministic replay and auditability.

Components:
1. `mission/optimization/search_space.py`: resolves tunable realistic-only parameters from registry + trust claims.
2. `mission/optimization/engine_v1.py`: deterministic coarse scan and local refinement.
3. `mission/optimization/constraints.py`: hard/soft constraint evaluation and risk metrics.
4. `mission/optimization/pareto.py`: non-dominated frontier extraction.
5. `mission/optimization/runner.py`: artifact-pack orchestration and determinism proofs.
6. `scripts/run_optimization.py`: CLI entrypoint for local/CI execution.

Contract boundaries:
1. Optimization runs only with `mode=realistic`.
2. Speculative or trust-`D` parameters are rejected before sampling.
3. Simulation core (`sim/**`) and golden checksum logic are unchanged.

Outputs:
- `OPTIMIZATION_CONFIG.json`
- `SEARCH_SPACE_RESOLVED.json`
- `SAMPLE_RESULTS.json`
- `PARETO_FRONTIER.json`
- `TOP_K_SOLUTIONS.json`
- `CONSTRAINT_VIOLATIONS.json`
- `DETERMINISM_CHECK.json`
- `meta.json`

## 14. Mission DAG Layer (v1)

Purpose:
1. Move mission evaluation from a flat parameter set to an explicit module DAG.
2. Preserve deterministic replay with per-module artifacts and hashchain integrity.
3. Keep realistic/speculative mode isolation intact while allowing module-level swapability.

Tracked contracts:
1. `mission/dag/schema/module_io.schema.v1.json`
2. `mission/dag/schema/scenario_dag.schema.v1.json`
3. `mission/dag/schema/failure_taxonomy.schema.v1.json`
4. `mission/dag/registry/module_registry.v1.json`
5. `mission/dag/registry/failure_taxonomy.v1.json`
6. `mission/dag/scenarios/mission_dag_baseline.v1.json`
7. `artifacts/mission_dag_v2_boundary.v1.json`

Runtime components:
1. `mission/dag/contracts.py`: contract validation, DAG resolution, module output validation.
2. `mission/dag/hashchain.py`: deterministic artifact hashchain and verification helpers.
3. `mission/dag/runner_v1.py`: topological DAG execution (realistic/speculative/dual).
4. `scripts/run_mission_dag.py`: proof-pack writer for DAG run artifacts.
5. `scripts/ci/mission_dag_validate.py`: strict schema/registry/scenario/artifact validator.
6. `scripts/build_mission_dag_v2_boundary_artifact.py`: generated v2 module-boundary review surface.
7. `scripts/ci/mission_dag_v2_boundary_validate.py`: strict validator for module rows, trace requirements, source hashes, and blocked claims.

Contract boundaries:
1. v1 modules are wrappers over mission baseline outputs and deterministic derived proxies.
2. Module outputs must match `module_io` envelope and taxonomy rules.
3. Any non-PASS module status must reference a known taxonomy ID.
4. Dual mode executes the full DAG twice and must preserve realistic isolation guarantees.
5. The v2 boundary artifact can require independent backend ids and state-trace hashes, but it must keep independent backend completion, high-fidelity traces, external reproduction, and flight-ready module claims false until external evidence exists.

Persisted run artifacts:
- `modules/<mode>/<node_id>.json`
- `hashchain.jsonl`
- `manifest.json`
- proof summaries (`DAG_RUN_SUMMARY.json`, `HASHCHAIN_PROOF.json`, `FAILURE_TAXONOMY_COVERAGE.json`)

## 15. Optimization Lab Layer (F1.1 Frontier + v2 Decision Surface)

Purpose:
1. Publish a deterministic, contract-bound realistic frontier artifact for public drilldown UX.
2. Promote roadmap item 10 into a generated four-axis decision surface.
3. Keep optimization explainability derived-only from tracked artifacts.
4. Prevent silent search-space and frontier drift.

Tracked contracts:
1. `artifacts/optimization_search_space.v1.json`
2. `artifacts/optimization_frontier_realistic.v1.json`
3. `artifacts/optimization_v2_frontier.v1.json`

Build/validate components:
1. `scripts/build_optimization_frontier.py`: deterministic realistic frontier builder from objective contract + parameter registry/claims + risk envelope contract.
2. `scripts/ci/optimization_frontier_validate.py --strict`: validates trust/domain bounds, 2D objective-vector integrity, pareto indices, and regeneration determinism.
3. `scripts/ci/risk_envelope_validate.py --strict`: validates risk method contract (`lower_quantile`), uncertainty-model reference, seed consistency, and deterministic regeneration.
4. `scripts/build_optimization_v2_artifact.py`: wraps the realistic frontier with `qualification_gap` and `cost_proxy` screening axes.
5. `scripts/ci/optimization_v2_validate.py --strict`: validates four-axis Pareto semantics, source hashes, non-certification boundaries, and deterministic regeneration.

CI enforcement:
1. Build frontier artifacts in `evidence` workflow.
2. Run strict validator.
3. Enforce no-drift with `git diff --exit-code` on optimization artifacts.

Boundary conditions:
1. No mutation of mission baseline or simulation core.
2. No reads from `ops/**`.
3. No speculative or trust-`D` parameters in realistic frontier.
4. The v1.1 source frontier remains `p_success` (maximize) and `risk_envelope` (minimize).
5. The v2 decision surface adds `qualification_gap` and `cost_proxy` as screening proxies, not qualification or procurement claims.
6. Public optimization artifacts must not publish registry-internal parameters or `code_literal.*` ids; those are summarized only via omission metadata/counts.

## 16. Evidence Layer

Purpose:
- Bind each mission parameter to explicit source IDs and trust grades.
- Keep realistic/speculative separation machine-checkable.
- Prevent silent trust-grade/source drift without changelog rationale.

Key contract files:
- `mission/EVIDENCE_SCHEMA_v1.json`
- `mission/EVIDENCE_REGISTRY_v1.json`
- `mission/UNCERTAINTY_MODEL_v1.json`

Enforcement path:
1. `scripts/ci/evidence_validate.py --strict` validates parameter coverage, source references, trust rules, and distribution bounds.
2. Drift guard checks `ParameterClaim`/`trust_grade`/`evidence_source_ids` diffs and requires `engineering/CHANGELOG.md` update.
3. `scripts/build_evidence_status.py` emits `artifacts/evidence_status_v1.json` for public status snapshot.

## 17. Parameter & Evidence Layer

Purpose:
- Maintain a machine-auditable canonical numeric inventory while keeping public mission/design/environment parameters separate from internal implementation literals through registry visibility metadata.
- Prevent silent introduction of new numeric constants without registry/evidence linkage.
- Produce deterministic sensitivity ranking for dominant `p_success` drivers.

Tracked contract files:
- `parameters/schema/parameter_registry.schema.v1.json`
- `parameters/schema/evidence_registry.schema.v1.json`
- `parameters/registry/parameter_registry.v1.json`
- `parameters/registry/parameter_literal_scope.v1.json`
- `parameters/registry/evidence_sources.v1.json`
- `parameters/registry/parameter_claims.v1.json`

Enforcement path:
1. `scripts/ci/parameter_literal_scan.py --strict` ensures every scoped numeric literal is mapped by `code_refs`/`json_refs` and every watched DAG/optimization file is either audited or explicitly excluded with rationale.
2. `scripts/ci/parameter_registry_validate.py --strict` validates units, bounds, classification, distribution structure, and public/internal visibility metadata.
3. `scripts/ci/parameter_evidence_validate.py --strict` validates source linkage, trust policy, and completeness ratio.
4. `scripts/ci/parameter_sensitivity_report.py` computes deterministic OAT ranking and top-5 dominant drivers.
5. Browser-facing parameter artifacts must use `visibility=public` and matching `public_surfaces`; internal `code_literal.*` ids remain in canonical registries for auditability only.
